## 4. Critical Rules Quick-Reference

> ⚠️ **Cached summary** — `directives/` là nguồn authority. Khi sửa directive liên quan, sync lại file này (nó được inject vào KNOWLEDGE_INDEX §4). Trước đây block này hardcode trong `knowledge_builder.py`; nay tách ra markdown để editable + diffable.

These are the most frequently needed rules, extracted from directives:

### Folder Structure (`folder_structure_sop.md`)
```
src/
├── @types/           # Augmented global types
├── bootstrap/        # App wiring: server, plugins, swagger
├── common/           # ABSTRACTIONS ONLY — NO infrastructure code
│   ├── cqrs/         # Pure POJO command/query bus & middlewares
│   ├── database/     # DB abstractions (ITransactionManager, AsyncLocalStorage context)
│   └── errors/       # Domain/Application error base classes
├── config/           # Env loading & validation (Zod)
├── container/        # Manual DI wiring (Fastify only, NestJS uses Modules)
├── infrastructure/   # Concrete implementations (Prisma, Fastify hooks, Pino logger)
├── modules/          # Feature modules by domain
│   └── <domain>/
│       ├── domain/           # Entities, Value Objects, Repo Interfaces (PURE TS)
│       ├── application/      # Command/Query Handlers (orchestration via interfaces)
│       ├── infrastructure/   # Concrete repos (PrismaXxxRepository), mappers
│       └── presentation/     # Routes/Controllers, Zod schemas
├── app.ts            # Root app factory (createApp)
├── main.ts           # Local entrypoint (listen)
└── main.lambda.ts    # AWS Lambda entrypoint
```

### Layer Boundaries — lint-enforced in core-api (`folder_structure_sop.md` §Enforcement)
> `apps/core-api/eslint.config.mjs` chặn import xuyên tầng qua `@typescript-eslint/no-restricted-imports` (bắt cả `import type`). Vi phạm = lint fail.
- `domain/**` → chỉ shared-kernel + relative. Cấm NestJS/Fastify, Prisma/`@/generated`, mọi tầng ngoài.
- `application/**` → cấm ORM/DB/HTTP infra + HTTP exceptions (`NotFoundException`…). Cho phép repo interface, `@/infrastructure/cqrs`, `@nestjs/common` DI (`@Injectable`/`@Inject`).
- `presentation/**` → cấm Prisma/`@/generated`, `@/infrastructure/database`. Đẩy qua CommandBus/QueryBus.
- `common/**` → cấm `@/modules`, `@/infrastructure`, NestJS, Fastify, Prisma. Chỉ shared-kernel + relative.
- **Ngoại lệ:** `@Injectable`/`@Inject`/`@CommandHandler` trong application = idiom DI hợp lệ NestJS (chỉ HTTP exception bị cấm).
- **Gate:** `npm run check` (= `turbo run typecheck lint format:check`). `typecheck` = `tsc --noEmit` bắt lỗi biên dịch lint bỏ sót. Fix: `npm run lint:fix` + `npm run format`.

### CQRS Pipeline (`cqrs_pattern.md`)
- Pipeline order: `LoggingMiddleware → RetryMiddleware → TransactionMiddleware → Handler`
- Retry wraps Transaction → each retry gets a fresh DB transaction
- Commands opt-in via `options: { transactional: true, retryable: true }`
- TransactionMiddleware uses `ITransactionManager` (abstract) + `AsyncLocalStorage`
- Repositories use `getTx() ?? this.prisma` — zero signature changes

### Domain Modeling (`domain_modeling.md`)
- Factories enforce invariants at construction — intention-revealing, not pass-through: `createOwner()` vs `createMember(role: ManageableOrgRole)`. Naming: ONE rule — `create<Variant>` (1 path → bare `create`; ≥2 → name all, no bare `create`), NEVER `createFor<UseCase>`.
- Security invariants via TYPE (compile-time) over runtime guards: `ManageableOrgRole = Exclude<OrgRole,'OWNER'>` → assigning OWNER is a compile error.
- **Validate on WRITE, TRUST on READ:** `rehydrate`/`mapper.toDomain` must NOT re-validate persistence. Data is validated by factory + Zod + DB constraints; a logically-wrong value on read is impossible (corruption = infra/ACID incident, not the domain's job). No `toX(row.role)` throwing validators on read — type the row as the Prisma enum and assign/narrow.
- Each entity has its own `infrastructure/mappers/<entity>.mapper.ts`; repos delegate, never `rehydrate(...)` inline.

### Database (`database_standard.md`)
- Primary keys: UUID (`@default(uuid())`), NEVER `autoincrement()`
- Naming: camelCase in code, `@map("snake_case")` in DB
- Soft delete: `deletedAt DateTime?` for important models
- Prisma v7: NO `url` in `schema.prisma`, use `prisma.config.ts`
- Port: `15432` (not default 5432)

### Testing (`testing_standard.md`)
- Co-location: `*.spec.ts` next to source file
- Mock pattern: `jest.Mocked<Interface>` with `as unknown as` cast
- ESM libraries: `jest.mock('uuid', () => ({ v7: jest.fn(() => 'mock-uuid') }))`
- Path alias: `@/` mapped via `moduleNameMapper`

### Validation (`zod_validation.md`)
- Zod is the ONLY validation library (no class-validator, no typebox)
- **Zod is the ONLY place for input validation** — no `if (!x.trim()) throw` in entity/factory. Every input boundary (HTTP, event consumer) validates via Zod; domain trusts clean input. Non-blank: `z.string().trim().min(1)` (`.trim()` BEFORE `.min`).
- Schema location: `modules/<module>/presentation/schemas/<action>.schema.ts`

### Logging (`logging_standard.md`)
- Dual-layer: HTTP hooks + CQRS LoggingMiddleware
- Use `createLogger(serviceName)` from shared-kernel
- NEVER `console.log`

### Security
- CORS origins from env vars, NEVER `['*']`
- Mandatory: `@fastify/helmet`, `@fastify/compress`, `@fastify/rate-limit`

## 5. Known Gotchas & Lessons Learned (from memory)

> These are real problems encountered during development.
> Search this section BEFORE debugging to avoid repeating mistakes.

- **Jest SyntaxError: Unexpected token 'export' khi import ESM từ shared-kernel** `[Unit tests auth-service]`
  → Bỏ isolatedModules trong ts-jest config package.json, dùng diagnostics.ignoreCodes: [151002] thay thế
- **Domain Entity: ensureCanLogin throw error chung chung Error()** `[Domain logic auth-service]`
  → Tạo UserCannotLoginError trong auth.error.ts và sửa lại entity
- **Entity data loss: rehydrate() method in User entity drops profile data** `[auth-service Domain Entity rehydration]`
  → Update the rehydrate() factory method to include profile in the recreated instance
- **Architecture: Microservice registered with wrong name 'api-gateway' instead of 'core-api'** `[core-api microservice communication]`
  → Fix service name registration in app.module.ts ClientsModule to match actual service name
- **Basic CommandBus lacks cross-cutting concerns (Middleware) like Logging/Transactions, leading to duplicated code in handlers.**
  → Implemented Onion Architecture Middleware Pipeline in CommandBus. execute(command) now uses recursive dispatch. Created ICommandMiddleware interface. Added LoggingMiddleware as proof of concept using the central logger.
- **Prisma transactions inside CQRS Middlewares break Hexagonal Architecture because Repositories require the 'tx' transaction client parameter explicitly, altering their signatures.**
  → Implemented AsyncLocalStorage for PrismaTransactionClient. The TransactionMiddleware initiates prisma. and saves 'tx' via AsyncLocalStorage context. PrismaRepositories simply use getTx() || this.prisma, completely decoupling infra transactions from the domain interface.
- **Middlewares in CQRS CommandBus apply globally, causing unnecessary Transaction/Retry overhead on commands that don't need them.**
  → Added CommandOptions to ICommand interface (transactional, retryable). Each Command declares its own needs. Middlewares check command.options at runtime and call next() immediately if not opted in. Infra-specific logic (isPrismaTransientError, PrismaTransactionManager) is injected at composition root.
- **Không chủ động cập nhật tài liệu (SOP) ngay khi có quyết định kiến trúc mới (CQRS Pure POJO) mà chỉ tập trung code.** `[directives/memory_sop.md, CQRS Module]`
  → Đưa việc cập nhật file .md trong thư mục directives/ và log memory trở thành bước BẮT BUỘC và TỰ ĐỘNG ngay lập tức mỗi khi có rule mới, không đợi user nhắc.
- **Framework code (NestJS modules) nằm lẫn trong common/cqrs/ phá vỡ quy tắc Pure POJO của CQRS Bus.** `[common/cqrs, infrastructure/cqrs]`
  → Bắt buộc đẩy các class có @Injectable(), @Module() (ví dụ: cqrs.module.ts) ra khỏi common/ và đưa vào infrastructure/cqrs/. Các Bus trong common/ phải là Pure TypeScript.
- **Query handlers reusing Domain Repositories (UserRepository) violates strict CQRS by fetching Entities instead of DTOs, and creating unused methods like findById on Write models.** `[CQRS architecture in modules/<domain>]`
  → Strictly separate Query vs Command Repositories. Put Command repos in domain/repositories/ (returning Entities) and Query repos in application/repositories/ (returning DTOs). Flatten infrastructure/repositories/ without commands/queries subfolders.
- **Infrastructure Leakage: Query Handlers directly importing PrismaClient** `[GetProfileHandler using PrismaClient]`
  → CQRS Query Handlers must depend on QueryRepository interfaces defined in the application layer, not infrastructure details like Prisma.
- **Query logic duplicated across multiple Handlers and DTOs (e.g. get-profile vs get-me)** `[auth-service get-profile and get-me redundancy]`
  → Strictly enforce DRY for Query/Read Models. If two queries return the exact same DTO and use the same infra logic, merge them into a single Query/Handler.
- **Props interface pass-by-reference leak in Domain Entity constructors breaking OOP Encapsulation** `[Domain Entity Constructors]`
  → Always clone the props object in the Entity constructor (e.g. `this.props = { ...props }`) instead of using `private readonly props: EntityProps` directly as a parameter property, to prevent external reference leaks.
- **Anemic Domain Model: Handler created empty entity then called update() to fill data** `[DDD Entity Creation Lifecycle]`
  → Intention-Revealing Interfaces (Factory Pattern): Entity creation must be atomic. Use Factory methods on the Entity (e.g. `createPremiumUser`, `createForLogin`, or pass initial data directly to `create`) instead of creating a hollow entity and letting the Application layer (Handler) manipulate it. This prevents the Transaction Script anti-pattern.
- **HTTP layer response shape (error body, success body, status-to-code mapping) duplicated across auth-service hooks và core-api interceptors/filters gây drift theo thời gian.** `[shared-kernel http utilities, auth-service hooks, core-api interceptors/filters]`
  → Extract 3 utility functions vào shared-kernel: httpStatusToCode(), buildErrorBody(), buildSuccessBody(). Cả hai service dùng chung — hook/interceptor/filter chỉ còn là thin wrappers gọi shared-kernel. Xem directives/logging_standard.md và directives/microservice_architecture.md.
- **shared-kernel/src/http/ có 6 file rời rạc, types bị tách khỏi classes liên quan (SuccessResponse ở build-success-body.ts, HttpResponseBuilder ở success-response.interface.ts), HttpResponseError nằm sai chỗ trong error-response.interface.ts.** `[shared-kernel http layer refactor]`
  → Gộp thành 2 file: response.ts (tất cả types+classes: BaseMeta, ErrorResponse, SuccessResponse, HttpResponseBuilder, HttpResponseError) và response.utils.ts (tất cả factory functions: buildErrorBody, buildSuccessBody, httpStatusToCode). Xoá 6 file cũ.
- **HttpResponseBuilder naming sai (không phải Builder Pattern) và HttpResponseError nằm trong http/ nhưng extends ApplicationError từ errors/ — sai chiều dependency.** `[shared-kernel http layer naming + structure]`
  → Rename HttpResponseBuilder → ApiResponse (data class, không phải builder). Move HttpResponseError → ResponseFormatError extends InfrastructureError vào errors/response-format.error.ts. http/response.ts giờ chỉ còn pure contracts (interfaces + ApiResponse data class). Dependency đúng: http/ import từ errors/, errors/ không import từ http/.
- **Event/messaging layer ráp ad-hoc, không neo vào pattern có tên → khó maintain, thiếu bản đồ** `[shared-kernel events+messaging, core-api outbox, worker-service feed]`
  → Chốt reference architecture trong directives/eventing_patterns.md: wire contract = CloudEvents 1.0 (CloudEvent<T>); transport selection = binder pattern (EVENT_TRANSPORT_MAP + CompositeMessagePublisher, Kafka+queue coexist); inbound = Message Dispatcher (EventRouter map type->handler, thay switch tay); domain event (in-proc EventBus) tách integration event (CloudEvents qua Kafka). Mỗi component ánh xạ EIP/eShop/Spring Cloud Stream/CloudEvents.
- **Nhầm: muốn 1 event nhiều phản ứng thì nhồi nhiều handler vào 1 EventRouter (router 1:N)** `[worker-service EventRouter, knowledge-events.consumer, eventing_patterns.md]`
  → Kafka-native: fan-out 1 event → N concern = N consumer GROUP riêng (mỗi concern 1 consumer + router 1:1, group id riêng theo concern). Router giữ 1:1, register() ném khi trùng type (guard). EventRouter scope per-module (rẻ, Map in-mem), KHÔNG global; KafkaClientService mới singleton (giữ connection).
